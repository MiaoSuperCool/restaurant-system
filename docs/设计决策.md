# 设计决策记录

这个项目里每个**非显然**的决定，以及当时的理由。

**为什么单独记一份**：这些理由原本散在代码注释和 commit message 里，读的人要翻十几个
commit 才拼得出来。这里按主题集中一次。

**格式**：每条写四件事——遇到什么问题 / 决定怎么做 / 为什么这么选 / 代价是什么。
只记「选了 A 没选 B 有原因」的那些；「用 MySQL 存数据」这种不需要记。

---

## 一、架构与组织

### 1. 一套后端 + 三套前端

**问题**：三个端（员工网页、员工小程序、顾客小程序）的用户和交互完全不同，
但业务规则是同一套。

**决定**：后端一套 API；三个前端同处一个 monorepo，目录按 `<载体>-<用户群>` 命名：
`web-staff` / `mp-staff` / `mp-customer`。

**为什么**：业务规则（算价、判权、库存扣减）绝不能有两个实现。三端各写各的后端，
等于三份算价逻辑，迟早对不上——而餐饮系统里「算错钱」是最不能接受的 bug。

目录名没用 `web-admin`：这个端的用户是收银员、店长、值班经理、运营主管、财务、老板，
只有老板那档才算传统意义的 admin。叫 admin 会把定位说窄，也和需求文档里
「内部人员网页端」的措辞对不上。

**代价**：三个前端要分别维护。但共享的是 API 契约和类型定义，这部分不重复。

### 2. 认证双轨：web 用 session，小程序用 token

**问题**：web 端和微信小程序端的认证方式天然不同。

**决定**：web 保留 Flask-Login 的 session + CSRF；小程序端走 token（微信登录换 openid → 签发 token）。

**为什么**：小程序拿不到、也不该依赖浏览器 cookie 会话；反过来在浏览器场景里，
session 更安全——HttpOnly 天然挡住 XSS 偷 token，CSRF 有成熟的防护方案。

关键约束：**两条通道共用同一套 service 层和权限判断**，只有「怎么认出这个人」不同。
不能因为认证方式不同就长出两套业务逻辑。

**代价**：认证有两条路径要各自测试。目前 token 那条还没实现（小程序端未开工）。

### 3. 员工与顾客拆成两套账号体系

**问题**：脚手架模板只有一张 `user` 表。

**决定**：`user` 改名 `staff`，加上门店归属、用工类型、公用账号标记；
顾客（`Member`）二期单独建表，不进权限码体系。

**为什么**：两者登录方式、字段、生命周期完全不同。员工走账号密码，有门店、角色、
用工类型；顾客走微信登录，只有 openid/手机号/昵称，量级几千到几万。硬塞一张表，
后面权限和字段会全打架。

**代价**：改名动了 50 个文件。趁库里只有 1 个账号时改的——那是最便宜的时候，
等三期员工/排班/报表全挂上去再改，成本高一个数量级。

## 二、权限

### 4. 权限分两层：能不能干 × 能碰哪些

**问题**：餐饮门店最容易踩的坑，是把「能不能干这件事」和「能碰哪些数据」当成一件事。

**决定**：两层。权限码（`dish:price:edit`）管能不能干，挂在角色上；
数据范围（本店 / 全部）也挂在角色上。

**为什么**：同一个 `dish:price:edit`，**店长和运营主管都有**。区别不在能不能改，
而在**能改哪些**——店长只能改本店的，运营主管能改全公司的。

如果把这个区别写进权限码，就得为每个角色各造一套
（`dish:price:edit:store`、`dish:price:edit:all`……），组合爆炸。

**代价**：每个查询都要记得带范围过滤。所以 service 层统一用
`current_user.accessible_store_ids()` 收口，返回 `None` 表示不限门店。
漏掉一处就是越权，所以有专门的测试守着。

### 5. 关联表用 `db.Table`，不建模成类

**问题**：角色-权限、员工-角色都是多对多。

**决定**：纯关联表（`db.Table`，复合主键）。

**为什么**：两个理由。

一是**关联本身没有额外属性**——没有授权时间、没有授权人、没有到期时间。

二是**复合主键能在数据库层挡住重复关联**：`(staff_id, role_id)` 做主键，
同一个员工同一个角色物理上不可能出现两条。如果建模成类，多出来的自增 `id`
当了主键，`(staff_id, role_id)` 就只是两个普通列，查重得靠代码——代码会漏。

**什么时候该改**：要做「临时授权到期」或「追责谁给谁授的职」时，
升级成关联对象（多几列 + 一版迁移），成本不高。现在不为想象中的需求买单。

### 6. 权限目录是代码，不是数据库里的数据

**问题**：37 个权限码 × 8 个角色，怎么维护。

**决定**：`backend/app/rbac.py` 定义目录和角色矩阵，`python manage.py seed-rbac` 幂等同步进库。

**为什么**：

- 权限是**业务规则**，应该和代码一起走版本控制——「谁把收银员的核销权限去掉了」能查 git blame
- 写错权限码**能当场报错**（seed 时校验），而不是等到某个店长发现自己改不了价才暴露
- 被改乱了能一键还原成设计文档定义的样子

**代价**：改权限要跑一条命令，不能只在界面上点。但一期本来就没做角色管理界面
（按需求文档是「先搭框架 + 少数角色」）。

### 7. 角色必须层层包含

**问题**：需求文档说「值班经理是受限版店长」，怎么保证这句话在执行时不走样。

**决定**：写成不变量，并用测试守住（`test_role_hierarchy_is_superset`）：

```
服务员 / 后厨  ⊆  收银员  ⊆  值班经理  ⊆  店长
```

**为什么**：这条**曾经被破坏过**——店长漏了 `order:create`，结果值班经理能点单、
店长反而不能。一个下属有而上司没有的权限，在真实门店里会直接卡住营业
（店长顶班时下不了单）。

**代价**：加新权限码时要多想一步「这个该从哪一层开始有」。但测试会提醒你。

### 8. 字段级权限：改价 ≠ 改菜名

**问题**：`menu:update` 管的是「改菜品」，那改价格算不算改菜品？

**决定**：接口挂 `menu:update`，但改 `base_price` 另需 `dish:price:edit`，
改 `status`（上下架）另需 `dish:online`。判断放在 service 层——因为只有那里
知道「改了哪个字段」。

**为什么**：需求文档把改价、上下架单独列成权限码，就是因为这两件事风险最高。
**门店里能改菜名的人，不一定该能改价格。**

**代价**：权限码变多，判断逻辑从装饰器挪到了 service。而且预置角色里恰好没有
「只改菜名不能改价」的组合，所以这条机制靠一个临时造角色的测试来守护。

## 三、数据建模

### 9. 菜品与门店解耦

**问题**：多店定价怎么做。

**决定**：`dish`（全公司一套：名称/图片/描述/分类/基础价）+ `store_dish`
（每家店一行：覆盖价、上下架、每日限量）。

**为什么**：如果直接在菜品表上放 `price`，六家店就得复制六条菜品记录——
菜品改个名要改六遍，统计「这道菜卖了多少」还要合并六行。需求文档把这条列为
「必须守住的第 5 条」，就是因为事后改这个结构的代价极高。

**代价**：查价要合并两层。所以有 `effective_price` 和 `_merge()` 把这件事收在一处，
调用方不用自己判断 `price` 是不是 `None`。

### 10. 门店菜品：「没有行 = 用默认值」

**问题**：要不要给每家店每道菜都建一行。

**决定**：不建。只有「这家店对这道菜做了特殊设置」才有一行；
没有行时按默认理解：用菜品基础价、可以卖、不限量。

**为什么**：6 家店 × 50 道菜 = 300 行。要求每家店每道菜都有行才能卖，
等于运营每加一道菜要手动上架 6 次。默认可用的话，新菜自动出现在所有门店，
哪家店不想卖再单独下架。

**代价**：任何查价的地方都要合并两层——同一个坑，同样靠收口解决。
另外「不传字段」和「传 null」是两个意思（不传 = 别动，null = 改回默认），
schema 里不能用 `load_default`，否则两者会变成同一个值、区分不出来。

### 11. 删除保护：扫外键，跳过 CASCADE

**问题**：每个实体删除前要检查「还有没有别的东西在引用我」。
手写一张「要检查哪些表」的清单迟早会漏。

**决定**：扫 SQLAlchemy metadata 里**所有**指向目标主键的外键；
其中 `ondelete='CASCADE'` 的**跳过**。

**为什么**：CASCADE 表示「从属/关联」——规格属于菜品、角色绑定属于员工，
父记录删了子记录跟着走，不算阻塞。RESTRICT / SET NULL 才是真正的「外部还在引用」。

关键洞察：**`ondelete` 这个参数本身就已经表达了「从属还是引用」**。
所以不需要再手工维护一份「哪些表算从属」的名单——直接读它。
建模时的意图，被复用成了运行时的判断依据。

**代价**：CASCADE 用错地方时这层保护会失效（把该保护的写成了 CASCADE）。
但那种情况下数据库自己的外键也会拦，不会静默产生脏数据。

## 四、交易

### 12. 下单价格一律后端算

**问题**：前端可以传价格吗。

**决定**：下单接口只收 `dish_id` / `quantity` / `option_ids`，**不收任何金额**。
前端传 `unit_price` 会被 schema 直接拒掉（未知字段 → 422）。

**为什么**：收银系统最基本的安全要求——**钱不能由客户端说了算**。
而且价格要按「本店实际价 + 规格加价」算，这个逻辑只能有一份，
放在后端是唯一能保证的地方。

**代价**：前端要显示价格得自己算一遍。但那个数字纯粹是给收银员看的，
提交时不传，后端重算。

### 13. 明细存快照，也保留引用

**问题**：菜品改名、涨价之后，历史订单要不要跟着变。

**决定**：菜名和单价存**快照**，同时保留 `dish_id` / `dish_option_id` 的**引用**。

**为什么**：两个都要，缺一不可。

- 快照负责**还原当时的样子**：运营明天把「牛肉面」改名成「红烧牛肉面」、
  涨价到 ¥40，历史订单必须还显示「牛肉面 ¥23」——否则月底对账时
  「这单到底卖了多少钱」说不清
- 引用负责**统计和分析**：「加蛋卖了多少份」用纯文本快照做不到，
  这正是规格要建两层表的理由

同样地，规格组/选项更新时**按 id 对齐**（改的原地改、新的新增、没出现的删掉），
不是全删重建——重建会让历史订单指到不存在的选项上。

**代价**：写入时多几个字段，更新规格时要写对齐逻辑而不是简单替换。

### 14. 支付记录单开一张表

**问题**：为什么不在订单上放个「已支付」布尔字段。

**决定**：独立的 `payment` 表，一个订单可以有多条。

**为什么**：

- 一个订单可能有**多笔支付**：组合支付（储值付一部分 + 现金付一部分）、
  先定金后尾款、线上支付失败重试
- 支付有**资金属性**：第三方流水号（微信支付单号）、支付时间、支付方式。
  **财务对账全靠这些**——月底要拿微信账单和我们的记录逐笔核，
  订单上一个布尔字段根本对不上

**代价**：订单上要维护 `paid_amount` 的累加，不能直接改状态了事。

### 15. 已收款的订单不能直接取消

**问题**：取消订单时已经收的钱怎么办。

**决定**：`paid_amount > 0` 时拒绝取消，返回「请先走退款流程」。

**为什么**：否则会出现「订单取消了但钱还在我们账上」——这是财务事故。
退款走独立的审批单（有流程、有留痕），批了才真的退钱。

**代价**：取消一个已收款的订单要多一步。但这个「麻烦」是故意的。

### 16. 单号做成可读的

**问题**：订单号用什么。

**决定**：`门店码-日期-当日序号`（`S001-20260912-0001`），不用 UUID。

**为什么**：顾客电话里报单号、店员在屏幕上一眼找单子，都要用它。
UUID 在这种场景下完全不可用。

**代价**：并发生成有撞号风险（靠唯一约束兜底，撞了整笔事务回滚重试）。
6 家店每分钟 20 单的量级下概率极低；真要做稳，生产环境该换 Redis INCR
或数据库序列。

### 17. 老系统共存：三张表，和一张「对账只做了一半」的坦白

**问题**：灰度切换期间新老两套系统并行跑，怎么保证数据不丢、账不乱。

**决定**：三张表各管一件事——`LegacyMap`（老号 ↔ 新对象）、`SyncRecord`
（每一次同步动作）、`Reconciliation`（每天的对账结论）。三者的设计理由写在
`models/legacy.py` 开头，这里只说两个**取舍**。

**取舍一：`LegacyMap` 没有外键。**

`target_id` 指向哪张表由 `target_type` 决定（多态引用），数据库层面建不了约束——
「映射指向一个已经被删掉的对象」数据库不会拦，只能应用层拦。换来的是
「以后要给订单、菜品也加映射」不用改表结构也不用再开两张表。
代价是明确的：`LegacyService` 里必须有一张 `TARGET_MODELS` 映射表，
每次 bind 都去查一遍对象存不存在。

**取舍二：对账只做了「自己跟自己」的那一半。**

    做了：  账户余额 vs 流水累加      订单实收 vs 支付流水
    没做：  我们的数 vs 老系统报的数  ← 需要老系统的日报，没有那个数据源

硬做另一半就只能编数据，那比不做更糟。但做的这一半不是凑数：设计文档说储值那
80 万要「一分不差」，**第一步就是先证明新系统自己记的账和流水是自洽的**。
账都自己跟自己对不起，跟别人比没有意义。

**代价**：`Reconciliation.store_id` 上没有唯一约束。虽然「同一天同一店同一类别
只该有一条」是对的，但储值那条记录 `store_id` 是空的，而 **MySQL 的唯一索引不拦
NULL**——一个只对一半生效的约束比没有更误导人。唯一性交给 service 保证
（每次跑对账先删同键的旧记录，对账的语义本来就是「重新下一遍结论」）。

**一个被测试抓出来的错**：原本「对不对得上」是看差异金额是不是 0。
测试里造了「一个会员多 100、一个会员少 100」——**合计正好抵消，差值是 0**，
于是被判成对得上，可这两处都是错的。所以加了 `mismatch_count`，状态由它决定。

## 附：还没解决 / 已知的坑

诚实记一下，免得下次重新踩：

- **订单号并发的正确解法**：见第 16 条。当前实现够用但不优雅。
- **前端表格的列宽**：内容区只有 892px（1440 − 侧边栏 200 − 用户卡 240 − 内边距 72）。
  列宽加起来超了不会出现滚动条，而是 `fixed="right"` 的操作列**盖住前一列**，
  看起来像渲染坏了。改列宽时记得重新加一遍总数，或者把次要信息并成一行小字。
- **演示数据不产生审计**：`seed-demo` 直接建模型对象（CLI 里没有请求上下文，
  走不了 service 层），所以审计记录是单独补的。真实操作走接口，会自动留痕。
- **被点过的规格选项删不掉，而且失败得很难看**：`order_item_option.dish_option_id`
  是 RESTRICT，选项一旦被订单引用，物理删除会被数据库拒绝。平时 `_sync_options`
  靠「按 id 原地改」绕开了这件事；但店长真要把某个加料从菜单上拿掉（提交时不带它）
  时，SQLAlchemy 会发一条 `DELETE FROM dish_option`，撞在 RESTRICT 上抛
  `IntegrityError`，最终是一个 500——错误文案是给 DBA 看的，不是给店长看的。
  `OrderItemOption` 的注释里写着「停用某个加料应该用别的方式（下架/改名保留）」，
  但那个「别的方式」还没做（`DishOption` 上没有上下架字段）。
  补法大致是：给 `DishOption` 加 `is_available`，让 `_sync_options` 把「没提交」
  翻译成「下架」，物理删除只留给从没被引用过的选项。
- **发券只做了「手动指定会员」这一种**：券模板、发券、券包、下单用券都通了，但发放
  方式只做了最不常用的那一种（一个个人选）。连锁餐饮真正的主力是另外三种，各自卡在
  不同的前置条件上，所以留着一起做：

  | 发放方式 | 场景 | 现在能不能做 |
  | --- | --- | --- |
  | 定向手动发 | 补偿、熟客维护，一次就几个 | **已做** |
  | 按条件圈人批量发 | 大促前圈「有储值的」「注册 30 天内的」，一次几百人 | 能做。但「按最近消费圈人」得先让演示订单挂上会员（现在全是散客单），否则圈不出人 |
  | 顾客自领（券中心） | 券挂在小程序里，顾客自己点领取，每人限领 N 张 | **卡在顾客端登录**——`mp-customer` 现在不登录，领了记不到谁头上 |
  | 自动发（新客/生日/消费满返） | 压根没有「发券」这个动作，是规则触发 | 能做，但要先定触发点（注册时？结账成功时？）和「每人限领」的计数口径 |

  真做批量发时有两个开关是**必须**的，不然重复点一下就重复发：**每人限领几张**、
  **已经有这张券的跳过**。而且圈人应该由后端按条件重新圈一遍（前端只传条件、不传
  名单）——前端手里那份名单可能已经过期，几百个 id 在请求里传也不像话。
