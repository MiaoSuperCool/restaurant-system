## 一、模型层

### 0. 先纠正三处结构性问题（不改，后面会疼）

1. **「用户」要拆成两个实体**：顾客（会员）和内部员工，登录方式、字段、生命周期完全不同。
    - 顾客 = 会员，走微信登录，只有 openid/手机号/昵称，量级几千到几万。
    - 员工 = 内部账号，走账号/手机号+验证码登录，有门店归属、角色、用工类型。
    - 硬塞一张表，后面权限、字段全打架。
2. **「菜品」要和「门店」解耦**：拆成「菜品基础」+「门店菜品」。
    - 菜品基础：名称、图片、描述、分类（全公司同一套）。
    - 门店菜品：某店某菜的价格、上下架、限量。**多店定价就靠这张关联表。**
3. **「优惠券」要拆成两张表**：「券模板」+「用户持券」。
    - 券模板：这个券长啥样、什么规则（运营主管发的那种）。
    - 用户持券：某个会员手里那张具体的券、状态、什么时候用的。
    - 只存一张表，核销统计、消耗统计全做不了。

### 1. 组织与账号域

- **门店 Store**（原稿漏列，核心）— 名称、类型（快餐店/堂食大店）、地址、营业状态、当前运行模式（老系统/新系统，用于灰度切换）
- **员工账号 Staff** — 姓名、手机号、登录凭据、归属门店 store_id、账号状态（启用/停用）、用工类型（全职/兼职）、是否公用账号
- **会员（顾客）Member** — 微信 openid、手机号、昵称、注册时间、状态；含**老系统 ID 映射**字段
- **角色 Role**（原稿已有）
- **权限 Permission**（原稿已有）— 用「权限码」，如 order:refund
- **用户-角色 UserRole**（补充，多对多）
- **角色-权限 RolePermission**（补充，多对多）
- **排班表 Shift**（补充）— 门店、员工、日期、班次、状态

### 2. 菜品与菜单域

- **菜品分类 Category**（补充），菜品分类为什么单独建一张表明明菜品表里已经有了分类字段，这是因为**分类本身有属性**，分类的**图标、是否显示、适用哪些门店**，运营主管要**增删分类、调顺序**——这是给它开的功能，如果分类是**写死的枚举、没有任何属性**（就"主食/饮品/甜点"三个值），那确实可以直接在菜品里放个字符串。==但餐饮分类**天天被运营改**，所以单独建表==
- **菜品 Dish**（原稿已有）— 名称、图片、描述、基础价、分类、状态
- **规格/选项 DishOption**（补充）— 份量、辣度、加料，带附加价；餐饮基本必备规格表怎么用，为什么必要：
```texy
菜品：牛肉面  ¥15
  规格组「份量」(单选，必选)      → 中份 +0 / 大份 +3
  规格组「辣度」(单选，必选)      → 微辣 +0 / 中辣 +0 / 特辣 +0
  选项组「加料」(多选)           → 加蛋 +2 / 加牛肉 +6

顾客选：大份 + 特辣 + 加蛋  →  15 + 3 + 2 = ¥20
订单明细记下：牛肉面(大份,特辣,加蛋)  ¥20
```
结构上是两层：**规格组**（份量/辣度/加料）→ **组内选项**（大份/微辣/加蛋），每个选项带加价。一道菜关联多个组，每组可设"单选/多选/必选"，**为什么不直接在菜品里写一行字？** ==因为要统计"加蛋卖了多少份"、要控"加牛肉"的库存、要统一改价。写死成文字，这些都做不了==
- **门店菜品 StoreDish**（补充，关键）— store_id、dish_id、覆盖价格、上下架状态、每日限量

### 3. 交易域

- **订单 Order**（原稿已有）— 单号、门店、会员/匿名单、来源（堂食/自取/外卖）、状态、金额（原价/优惠/实付）、**操作人（谁下的单，含服务员代点）**、时间
- **订单明细 OrderItem**（补充）— 菜品、规格、数量、单价、小计
- **支付记录 Payment**（补充）— 订单、支付方式（微信/现金/储值/团购券）、金额、第三方流水号、时间
- **退款申请单 Refund**（补充，独立实体）— 订单、发起人、原因、金额、**类型（线上/线下补录）**、审批人、审批状态、时间
- **退款流水 RefundTxn**（补充）

> ==退款为什么必须独立成单==：客户明确要求「线下退款即使口头商量也要补录、要留痕」，天+审批流，不是订单上一个状态字段能装的。
> ==支付记录为什么单开==：一个订单可能有**多笔支付**：组合支付（储值付一部分 + 现金付一部分）、先定金后尾款、线上失败重试；支付有**资金属性**：第三方流水号（微信支付单号）、支付时间——**财务对账全靠它**
> ==退款流水表的作用==：跟支付对称——**支付记"进账"，退款流水记"出账"**；**退款申请单**是**流程**：谁申请、谁批、批没批。批了 ≠ 钱退了，**退款流水**是**钱真的退出去**那一刻的记录：金额、时间、退到哪、流水号

### 4. 会员资产域

- **储值账户 Balance**（补充，关键）— member_id、余额；过渡期**以老系统为权威、新系统只读**
- **余额流水 BalanceTxn**（补充，关键）— 账户、类型（充值/消费/退款/迁移）、金额、变动后余额、关联订单/老系统单号、时间
- **积分账户 Points**（补充）— member_id、积分
- **积分流水 PointsTxn**（补充）
- **老系统 ID 映射 LegacyMap**（补充）— 会员/储值 跨系统对应关系

> **余额绝不能用「一个数字字段」糊弄**，必须有流水账。那 80 万要一分不差，全靠流水能对得上。

### 5. 营销域

- **券模板 CouponTemplate**（补充）— 类型（满减/折扣/赠品）、面额、门槛、有效期、适用门店/菜品、发放数量
- **用户持券 UserCoupon**（补充，关键）— 券模板、会员、状态（未用/已用/过期）、领取时间、使用时间、**核销门店**
- **活动 Campaign**（补充）— 名称、类型、门店范围、时间、状态

### 6. 库存域

- **门店库存 StoreInventory**（补充）— 门店、原料/菜品、数量、预警值
- **库存变动流水 InventoryTxn**（补充）— 类型（入库/消耗/盘点/同步）、数量、关联订单、时间

### 7. 审计与对接域

- **审计日志 AuditLog**（原稿已有）— 操作人、角色、动作、目标对象、变动前后值、IP、时间
    - **必须覆盖的动作**：改价、发券、退款、开/停账号、登录、核销
- **同步记录 SyncRecord**（补充）— 对接对象（老 SaaS / ERP）、方向、数据类别、状态、时间、错误信息
- **对账记录 Reconciliation**（补充）— 日期、门店、类别（订单/储值）、期望值、实际值、差异、状态

### 8. 辅助（一期可后置）

## 二、角色与权限

### 原稿漏掉的角色（补上）

1. **值班经理 / 副店长** — 店长不在时顶班，是「受限版店长」：大额退款批不了。
2. **兼职 / 小时工** — 不是独立角色，是一种**账号类型**：套「收银员/服务员」的权限，但账号要能**秒开秒停**。

### 两个认知纠正

1. **顾客不是一个「内部角色」** — 它是另一套账号体系（会员），走微信登录，**不进权限码体系**。别把它和员工角色混在一张表里管。
2. **服务员用「公用账号」** — 但每次下单要**记录实际操作人**（选人/扫工牌），否则追责无门。

### 角色 × 权限（修订版）

- **顾客（会员端，非权限码体系）**：浏览菜单、下单、支付、查自己订单、用券、查余额/积分。（**数据范围：仅自己**）
- **服务员**：order:create（代客点单）、order:view（本店）。（**数据范围：本店**；公用账号，记录操作人）
- **后厨**：order:view（本店出单）。（**数据范围：本店**）
- **收银员**：order:create、order:receive、pay:collect、coupon:verify、member:balance:view、refund:apply。（**数据范围：本店**）
- **值班经理 / 副店长**：收银员全部 + order:cancel、refund:approve（限额内）、report:store、stock:view、schedule:manage（临时）。（**数据范围：本店**）
- **店长**：order:view（本店）、refund:apply、refund:approve、menu:update（本店）、dish:price:edit（本店）、dish:online（本店）、report:store、stock:view/manage、staff:manage（本店：收银/服务员/后厨/兼职）、schedule:manage。（**数据范围：本店**；不能发全店券、不能改总部活动、不能看别店）
- **运营主管**：menu:create/update/delete（全）、dish:price:edit（全）、campaign:manage、coupon:issue（全）、store:view、member:manage、report:all。（**数据范围：全部**）
- **财务**：finance:view、finance:export、report:all、refund（查看全部）、member:balance:view（全）、sync:view。（**数据范围：全部**；不能碰菜单/价格）
- **老板**：**管理层权限**——store:manage、staff:manage:all（店长/总部账号）、menu:*、dish:*、report:all、finance:view/export、refund:approve(:large)、audit:view、sync:view 等。（**数据范围：全部**）
  **不是「全部权限」**：order:create / order:receive / order:cancel / pay:collect / coupon:verify / refund:apply / member:balance:recharge / points:adjust / stock:manage 都不给——那些是在柜台上动手、产生业务数据的活。判据是「管」还是「干」，见 `rbac.py` 里那段注释

### 数据范围（易漏，必须后端强制）

- **本店**：收银员、服务员、后厨、值班经理、店长
- **全部**：运营主管、财务、老板
- 规则：前端只负责「显不显示」，后端负责「能不能干 + 能碰哪些数据」。

## 三、必须守住的 6 条

1. **余额和积分必须有流水账**，不能只存一个数字。
2. **优惠券拆两张表**：券模板 + 用户持券。
3. **退款一律走审批单**，线下退款也要补录、要留痕。
4. **审计日志覆盖关键动作**：改价、发券、退款、开停账号、登录、核销。
5. **多店定价靠「门店菜品」关联表**，别在菜品上写死价格。
6. **与老系统共存靠**「同步记录 + 对账记录 + ID 映射」三件套。
