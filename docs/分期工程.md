**一期：核心交易闭环（MVP）**

目标：跑通"顾客下单 → 付款 → 门店接单"这一条链路。

1. 基础数据：门店、菜品分类、菜品、规格、**门店菜品（多店定价）**。
2. 顾客小程序：浏览菜单、点单（堂食/自取/外卖）、下单、支付（先用沙箱/模拟）。
3. 收银端（网页）：接单、收款、核销团购券、打小票。
4. 后台管理网页：菜单、门店、员工的**基础管理**。
5. 权限体系地基：登录、角色、权限码、数据范围（先搭框架 + 少数角色）。
6. 顺手做**技术验证（spike）**：微信支付、ERP 接口、老系统导出，先确认走得通。

验收：顾客能下单付款、门店能看到并接单，全链路跑通。

**二期：会员与营销 + 老系统共存**

目标：会员资产能玩起来，且钱对得上。

1. 会员：注册、档案、微信登录。
2. 储值账户 + **余额流水** + 充值；积分账户 + 积分流水。
3. 优惠券：券模板 + 用户持券 + 领券/用券/核销；活动。
4. 员工小程序：服务员**代点单**、后厨出单、券核销。
5. 老系统共存：同步记录 + 对账记录 + ID 映射，**储值 80 万迁移**。
6. 审计日志（关键动作留痕）。

验收：储值/发券/核销能跑，迁移后余额一分不差，日常对账通过。

**三期：多角色管理与经营分析**

目标：管理层能看数、能管人。

1. 店长端：本店报表、改价/上下架、退款审批、排班、本店员工和**兼职账号秒开秒停**。
2. 运营主管：全店菜单/价格/活动/发券。
3. 财务：营业额/储值/退款、导出表格。
4. 老板：6 家店看板、红黑榜、异常预警、管理店长账号。
5. 库存管理 + 库存流水。
6. 操作留痕全覆盖（改价、发券、退款、开停账号）。

验收：老板能看到全局 6 家店、各角色各管各的、权限拦得住。

**四期：ERP 对接、优化与上线**

目标：对接收尾、性能兜底、正式切上线。

1. ERP 自动同步 + 对账可视化（"传没传成功"看得见）。
2. 性能优化 + **午餐高峰压测**（每分钟 20+ 单）。
3. **按门店灰度切换**（一店一店从老系统切到新系统）。
4. 正式上线、监控、老系统退场准备。

验收：ERP 数据自动同步、对账一致、高峰期不卡、门店平滑迁移。

**附：顾客端入口的演进**

一期顾客端的入口是「从门店列表里选一家」——这是演示期的简化，不是真实形态。
`mp-customer/README.md` 写的是「顾客扫码进店」，但那条链路目前只存在于文字里，
代码里是列表选店。**这个落差要认下来，它是一期最不像真实产品的一处。**

真实的自营连锁里，找店的优先级是：

    扫码进店（扫桌上的码 → 直接进这家店的菜单）   ← 主入口，覆盖绝大多数场景
       ↓
    首页门店介绍 + 点单处才选门店                  ← 兜底（顾客在家里先看看）
       ↓
    定位推荐最近门店                               ← 锦上添花

| 做什么 | 哪一期 | 为什么 |
| --- | --- | --- |
| 扫码进店的**参数链路** | **二期** | 只有它能真正解决「选门店页不像真实产品」。而且现在就能做——`?storeId=19` 这条页面参数的路已经通了；真二维码要正式 AppID，可以先用手拼的链接把链路跑通 |
| 首页改成门店介绍、点单入口里再选店 | **二期** | 零依赖，和扫码一起做。门店表要加展示字段（简介、营业时间、图片） |
| 定位推荐 | **三期** | **门店得先有真实经纬度**（`Store` 现在只有 `address` / `phone`）。演示数据编几个假坐标，推出来的「最近门店」就是假的，反而露怯 |

**顺序不能反**：扫码是主入口，定位是「兜底之上的兜底」。反过来做的话，定位那套东西
在扫码场景里是浪费的——**顾客都站在店里了，还定位干什么。**

（为什么不做成「进小程序先看餐馆基本信息、按定位选店」那种形态？那是**平台型**小程序
——美团、大众点评，顾客在家里还没决定去哪家。自营连锁的顾客就坐在店里，不需要「找店」。
两者的入口逻辑不一样。）

**一句话**：**一期能下单，二期有钱和会员，三期能管能看，四期能对接能上线。** 一、二、三期是硬核，四期是收口
