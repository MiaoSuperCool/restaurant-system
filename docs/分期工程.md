**一期：核心交易闭环（MVP）**

目标：跑通"顾客下单 → 付款 → 门店接单"这一条链路。

1. 基础数据：门店、菜品分类、菜品、规格、**门店菜品（多店定价）**。
2. 顾客小程序：浏览菜单、点单（堂食/自取/外卖）、下单、支付（先用沙箱/模拟）。
3. 收银端（网页）：接单、收款、核销团购券、打小票。
4. 后台管理网页：菜单、门店、员工的**基础管理**。
5. 权限体系地基：登录、角色、权限码、数据范围（先搭框架 + 少数角色）。
6. 顺手做**技术验证（spike）**：微信支付、ERP 接口、老系统导出，先确认走得通。

验收：顾客能下单付款、门店能看到并接单，全链路跑通。

**二期：会员与营销 + 老系统共存**

目标：会员资产能玩起来，且钱对得上。

1. 会员：注册、档案、微信登录。
2. 储值账户 + **余额流水** + 充值；积分账户 + 积分流水。
3. 优惠券：券模板 + 用户持券 + 领券/用券/核销；活动。
4. 员工小程序：服务员**代点单**、后厨出单、券核销。
5. 老系统共存：同步记录 + 对账记录 + ID 映射，**储值 80 万迁移**。
6. 审计日志（关键动作留痕）。

验收：储值/发券/核销能跑，迁移后余额一分不差，日常对账通过。

### 进度到此为止：先转部署上线

**2026-09-18 决定：三期做到「排班」为止，剩下四项（活动、财务导出、红黑榜、
库存）停下来，先部署上线。**

理由：这是个**求职作品**，说服力在「能点开看」，不在「清单更长」。
三期已经做完的部分（多角色、数据范围、报表、排班）本身就够撑起一次演示；
再往里加一块没做完的模块，边际收益递减，而部署这件事是**从 0 到 1**——
现在它只能在本机跑，别人看不到。

停下来的这四项，各自都不是「差一点就完」的状态，而是**完整没开始**：

    活动     要先定叠加规则（和券、积分三者谁先算），是设计活，不是编码活
    导出     CSV 本身不难，难的是先定「导出哪些列、按什么口径」——不定就是白导
    红黑榜   指标口径得先有数据量支撑，演示数据那 12 笔订单排出来的「榜」是编的
    库存     整整一块空白域（入库/盘点/流水/损耗），半块不如不做

**顺序是「先让它能被看到，再让它更全」。** 部署完再回来接着做，
这份清单原样等着，不用重排。

目标：对接收尾、性能兜底、正式切上线。

**附：顾客端入口的演进**

一期顾客端的入口是「从门店列表里选一家」——这是演示期的简化，不是真实形态。
`mp-customer/README.md` 写的是「顾客扫码进店」，但那条链路目前只存在于文字里，
代码里是列表选店。**这个落差要认下来，它是一期最不像真实产品的一处。**

真实的自营连锁里，找店的优先级是：

    扫码进店（扫桌上的码 → 直接进这家店的菜单）   ← 主入口，覆盖绝大多数场景
       ↓
    首页门店介绍 + 点单处才选门店                  ← 兜底（顾客在家里先看看）
       ↓
    定位推荐最近门店                               ← 锦上添花

| 做什么 | 现状 |
| --- | --- |
| 首页改成门店介绍、点单入口里再选店 | **做掉了**。顾客端重构成底部四个 tab 之后，首页就是门店介绍（简介、营业时间、地址、电话），门店选择挪到了那张卡片上（`stores/currentStore.ts`）。没有做「图片」——门店照片是另一件事，演示数据里编几张假图反而露怯 |
| 扫码进店的**参数链路** | **没做**。`?storeId=19` 这条页面参数的路是通的（`onLoad` 里读一下就行），差的只是「进小程序先落在哪一页」。真二维码要正式 AppID，可以先用手拼的链接把链路跑通 |
| 定位推荐 | **没做**。**门店得先有真实经纬度**（`Store` 现在只有 `address` / `phone`）。演示数据编几个假坐标，推出来的「最近门店」就是假的，反而露怯 |

**顺序不能反**：扫码是主入口，定位是「兜底之上的兜底」。反过来做的话，定位那套东西
在扫码场景里是浪费的——**顾客都站在店里了，还定位干什么。**

（为什么不做成「进小程序先看餐馆基本信息、按定位选店」那种形态？那是**平台型**小程序
——美团、大众点评，顾客在家里还没决定去哪家。自营连锁的顾客就坐在店里，不需要「找店」。
两者的入口逻辑不一样。）

**一句话**：**一期能下单，二期有钱和会员，三期能管能看，四期能对接能上线。** 一、二、三期是硬核，四期是收口
