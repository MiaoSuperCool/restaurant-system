# 部署

给「把链接发给别人点开看」这个场景写的。**一台有公网 IP 的云服务器 + Docker**，
三条命令起起来，不需要域名、不需要 HTTPS（要加也写了，见最后一节）。

## 部署完是什么样

一个地址，三个入口，都在这一个域名（或 IP）下面：

```
http://<你的服务器地址>/            内部人员网页端（店长/老板/收银员用）
http://<你的服务器地址>/customer/   顾客端（手机打开：扫码点单那一套）
http://<你的服务器地址>/staff/      员工端（手机打开：代客点单、出单、我的班表）

http://<你的服务器地址>/api/docs    接口文档（Swagger）
```

**为什么是三个路径而不是三个域名**：这三个前端是同一套后端的三个客户端，
放一起就不用配跨域（`FRONTEND_ORIGINS` 留空即可），别人也只需要记一个地址。
路径前缀是**构建时**写进产物里的（两个 uni-app 的 `H5_BASE`，见各自 `vite.config.ts`），
后端只负责照着路径把文件发出去。

**两个小程序端放的是 H5 版**：微信小程序真机要正式 AppID + 备案域名，
求职作品没有这些（`manifest.json` 里的 appid 是空的），
所以线上给别人看的是同一套代码的 H5 产物——界面和交互是一样的。

## 服务器要什么

- 一台能装 Docker 的 Linux（2 核 2G 就够，镜像构建那几分钟吃点内存）
- 装好 Docker Engine + Compose 插件：`curl -fsSL https://get.docker.com | sh`
- 安全组/防火墙放行你要用的端口（默认 5000；用 `APP_PORT=80` 就放行 80）

## 三步

```bash
# 1. 拉代码
git clone <你的仓库地址> restaurant-system && cd restaurant-system

# 2. 写 .env（**在仓库根目录**，不是 backend/.env——那份是本地开发用的）
cat > .env <<'EOF'
DB_PASSWORD=换个数据库密码
SECRET_KEY=换成一串随机的
EOF
# SECRET_KEY 生成方法：openssl rand -hex 32
# **一定要换**：不换就是代码里那个 "change-me"，session 会被人伪造

# 3. 起（第一次要构建三个前端 + 装 Python 依赖，几分钟）
docker compose up -d --build
```

然后浏览器打开 `http://<服务器地址>:5000`，用 `dianzhang / Demo123!` 登录。

看启动过程：`docker compose logs -f app`。

## 容器第一次启动时自动做的事

`docker-compose.yml` 里那串 `command` 就是开机自检流程，顺序是有讲究的：

```
flask db upgrade              建表/迁移
python manage.py create-admin 建超级管理员（admin / Admin123!）
python manage.py seed-rbac    灌权限码和预置角色
python manage.py seed-demo    灌演示数据（--if-empty：库里已有门店就跳过）
gunicorn -w 4                 起服务
```

三个注意点：

- **`seed-rbac` 不能省**。不跑的话所有角色一个权限都没有，登录进去什么都点不动
  （除了 admin，它是超管，绕过权限判断）
- **`seed-demo` 带 `--if-empty`**：订单数据不是幂等的，不带这个每次重启都多 12 笔演示订单
- **`create-admin` 必须把 `--name` / `--mobile` 也传上**。这两个参数带 `prompt`，
  容器里没有 stdin，不传的话 Click 会直接 `Aborted!` 退出，后面那串 `&&` 全都不执行，
  gunicorn 根本起不来（**这个坑真踩过**，在本机复现的）

## 小内存机器：前端改成在本地构建

`docker compose up -d --build` 会在服务器上跑三个前端构建（每个都是 `npm ci` + `vite build`）。
这一步**很吃内存**：一个 node 构建峰值七八百兆，三个阶段 BuildKit 还会**并行**跑。
1G~2G 的小机器会被打满，表现是**ssh 都登不进去**，得去云控制台强制重启。

判断标准：`free -h` 里 Mem 那行的 `total` **小于 4G**，就走这条路。

思路很简单——**把吃内存的那一步挪到你自己电脑上**，服务器只负责装 Python：

    本地    构建三个前端  →  打包
    上传    把包 scp 上去
    服务器  用 prebuilt 那套装镜像（不跑 node，两分钟）

### ① 本地构建三个前端

```bash
cd web-staff && npm run build && cd ..
cd mp-customer && MSYS_NO_PATHCONV=1 H5_BASE=/customer/ npm run build:h5 && cd ..
cd mp-staff && MSYS_NO_PATHCONV=1 H5_BASE=/staff/ npm run build:h5 && cd ..
```

> `MSYS_NO_PATHCONV=1` 是 Git Bash 的坑：不加的话 `/customer/` 会被它当成路径
> 转换成一串 Windows 路径（试过 `/Application/Git/customer/`），产物里的资源引用就全错了。
> Linux/macOS 上不用加。

### ② 打包成 `prebuilt/` 这个结构

```bash
mkdir -p prebuilt \
  && cp -r web-staff/dist prebuilt/web-staff \
  && cp -r mp-customer/dist/build/h5 prebuilt/mp-customer \
  && cp -r mp-staff/dist/build/h5 prebuilt/mp-staff \
  && tar czf prebuilt-dists.tar.gz prebuilt
```

（`prebuilt/` 和这个压缩包都在 `.gitignore` 里——它是构建结果，不该进仓库。）

### ③ 传上去、解开

```bash
scp prebuilt-dists.tar.gz root@<你的服务器>:/opt/restaurant-system/
```

```bash
cd /opt/restaurant-system && tar xzf prebuilt-dists.tar.gz && ls prebuilt
```

→ 应该列出 `web-staff` / `mp-customer` / `mp-staff` 三个目录

### ④ 用 prebuilt 那套起（**注意是两个 `-f`**）

```bash
docker compose -f docker-compose.yml -f docker-compose.prebuilt.yml up -d --build
```

覆盖文件里只改了一处：app 服务换成 `Dockerfile.prebuilt`。MySQL、Redis、
启动自检那串命令、端口，全部还是 `docker-compose.yml` 里那份。

### 代价

**前端产物不在服务器上构建了**——改了前端代码，要重新走一遍「本地构建 → 打包 → scp」。
后端改了不受影响（还是 `git pull` + 重新 `up`）。

这是拿「部署的自动化」换「能在小机器上跑起来」，对小机器是划算的；
机器够大就别用这条路，`docker compose up -d --build` 一条命令更省心。

## 常用命令

```bash
docker compose ps                        # 三个容器在不在
docker compose logs -f app               # 看后端日志
docker compose restart app               # 改了 .env 之后重启
docker compose down                      # 停（数据在卷里，不会丢）
docker compose up -d --build             # 更新代码后重新部署

# 想重新灌一遍演示数据（会清掉订单/会员/排班，再从头建）
docker compose exec app python manage.py seed-demo --reset

# 老系统共存那一摊（对账页要有数据才好看）
docker compose exec app python manage.py import-legacy
docker compose exec app python manage.py reconcile

# 数据库备份（演示数据也是数据，讲砸了还能退回来）
# 密码用容器里那个变量：compose 把它从 .env 的 DB_PASSWORD 传进去了
docker compose exec db sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" restaurant_system' > backup.sql
```

## 上线前请务必改掉的两件事

**1. `SECRET_KEY` 必须换**（上面写了）。不换的话 session cookie 是可以伪造的，
任何人都能把自己改成 admin。

**2. 想清楚 admin 密码**。默认是 `Admin123!`，而这个项目是**公开演示**——
演示账号的密码都写在 README 里（`Demo123!`），有人拿 admin 登进去能把数据删光。
三个选择：

- 演示环境的数据库本来就是一次性的 → **接受它**，但别往里放任何真实数据
- 改掉：**第一次启动之前**就在 `.env` 里写 `ADMIN_PASSWORD=...`。
  已经建过之后 `create-admin` 只会提示「已存在」，它不改密码——
  那时候要改得先进后台（员工页）把这个账号删掉，再跑一遍启动脚本
- 最省事：**别把 admin 的密码告诉任何人**，演示一律用 `laoban` / `dianzhang` 这些演示账号

（`admin` 是超管，能用所有功能；演示账号各有各的角色，**演示权限体系反而更好用它们**——
换个账号登录，菜单和按钮都不一样，这是这个项目最值得看的地方。）

## 域名：备案绕不过去（实测记录）

**结论先放这儿：大陆服务器 + 没备案的域名，用域名访问就是不通；用 IP 访问完全没问题。**

下面这段是 2026-09-18 实际部署时测出来的，四条都是**实测推翻了猜测**：

    cestamiao.top              → 能用（那是服务器上另一个项目，说明这个域名在阿里云的白名单里）
    restaurant.cestamiao.top   → 阿里云的备案拦截页（"请等待域名备案或恢复访问"）
    cestamiao.top:18080        → **也拦**。非标准端口不放过
    http://120.26.65.242/      → 能用 ✓ ← 最终就是这么上线的

两个认识，跟传闻不一样：

1. **拦截是按「请求里的域名」查的，不分端口。** 网上流传的"换个端口绕过备案"，
   在阿里云这里不成立——80、443、18080 一视同仁。我一开始也按传闻判断过，被实测打脸。
2. **用 IP 访问压根不触发这个检查。** 备案是跟域名绑的，Host 里没有域名就没有"这个
   域名备案了没有"这回事。所以「IP + nginx(80) → 容器」是一条能立刻用的路，
   代价只是地址不好看。

所以最终形态是：

```
http://<服务器IP>/            网页端
http://<服务器IP>/customer/   顾客端
http://<服务器IP>/staff/      员工端

nginx 监听 80（server_name 写的是那个 IP）
  └─→ 127.0.0.1:18080（容器里的 gunicorn）
```

**要域名的话，只有一条路：备案。** 自己的域名 + 自己的服务器，材料齐了就能提交，
一般 1~3 周。下面那套配置就是给备案下来之后准备的。

## 挂域名 + HTTPS（备案下来之后再做）

备案通过之后再走这里，一共五步。

### 1. 域名解析

在域名服务商那里加一条 A 记录，指向服务器公网 IP。

> 加完先确认能解析：`getent hosts 你的域名` 能出服务器 IP 就行。
> **别用 `ping` 判断**——云服务器默认在安全组里禁 ICMP，ping 不通是正常的，
> 拿它当依据会误判。

### 2. 容器只监听本机

nginx 顶上来了，就不用把容器暴露到公网。仓库根 `.env` 里：

```
APP_PORT=127.0.0.1:18080
```

（`APP_PORT` 拼进 `ports:` 里，所以这里写的是「宿主机那一段」——
带上 `127.0.0.1:` 就只有本机的 nginx 能连它。**用 18080 不用 5000**：
VPS 上常有别的项目占着 5000，撞上去容器起不来，实测踩过。）

改完 `docker compose up -d` 重建容器。

### 3. nginx 配置

**别手敲**——配置文件在仓库里（`deploy/nginx.conf`），复制过去就行：

```bash
cd /opt/restaurant-system
# 把 server_name 换成你的域名（按行号改整行，命令里不带中文，不会因为粘贴丢字而不生效）
sed -i '16s/.*/    server_name 你的域名;/' deploy/nginx.conf
grep server_name deploy/nginx.conf

cp deploy/nginx.conf /etc/nginx/sites-available/restaurant
ln -sf /etc/nginx/sites-available/restaurant /etc/nginx/sites-enabled/restaurant
nginx -t && systemctl reload nginx
```

> **为什么走「仓库里放配置文件 + cp」而不是在服务器上 `cat > ... <<EOF`**：
> 这段配置十几行、还带 nginx 的 `$` 变量，从聊天窗口或文档里复制到终端很容易粘坏——
> 少一行（尤其是结尾那个 `EOF`）终端会一直卡在 `>` 提示符上下不来。
> 实际部署时就是这么被坑的。

**这个文件也可以直接拿来服务 IP**（把 `server_name` 写成服务器公网 IP 就行）——
没有域名的那条路就是这么走的，见上面「域名：备案绕不过去」那节。

### 4. 证书

```bash
apt install -y certbot python3-certbot-nginx
certbot --nginx -d 你的域名        # 会自动改写上面的 nginx 配置，加上 443 和跳转
```

### 5. 打开 cookie 的 Secure

**这一步不做也能跑，但不该不做**：外面是 https，容器和 nginx 之间是 http，
容器自己看不出区别，所以「session cookie 要不要带 Secure」得显式告诉它。

```bash
echo 'SESSION_COOKIE_SECURE=true' >> .env
docker compose up -d
```

改完验证一下：登录后浏览器开发者工具里看那条 `session` cookie，
应该带 `Secure` 和 `HttpOnly` 两个标记，`SameSite=Lax`。

> 这一条是**这次部署顺手修掉的一个坑**：`ProductionConfig` 原来把它写死成 `True`，
> `docker-compose.yml` 里那句开关怎么改都不生效——写死的时候，
> 用 IP 直接访问（http）会表现为「登录点了没反应」
> （POST 明明 200，下一个请求却是未登录，因为浏览器不回传 Secure 的 cookie 到 http）。

## 部署那天踩到的坑（按时间顺序）

2026-09-18 第一次真机部署，一晚上踩了七个。**共同点是本地全都测不出来**——
所以这份清单值得完整读一遍，比上面那些步骤更省时间。

| # | 现象 | 原因 | 修法 |
| --- | --- | --- | --- |
| 1 | `npm ci` 失败 `exit code: 1` | 大陆直连 registry.npmjs.org 超时；`npm ci` 不像 `npm install` 会重试 | Dockerfile 加 `NPM_REGISTRY` 构建参数（`.env` 里可换源） |
| 2 | 构建把机器打满、ssh 登不进去，只能去控制台强制重启 | **1.6G 内存 + 零 swap**；而且 BuildKit 把三个独立阶段**并行**跑，等于三份 npm ci 同时上 | ① 加 4G swap ② 三个阶段合并成一个（同阶段的 RUN 只能顺序执行）③ 小机器改走「前端本机构建」那条路 |
| 3 | 容器起不来：`failed to bind host port 127.0.0.1:3306` | VPS 上本来就装着 MySQL | 把 `db` 的端口映射去掉——**镜像里那个 MySQL 不需要暴露给宿主机** |
| 4 | 又撞：`bind host port 0.0.0.0:80` | nginx 占着 80（另一个项目的） | 改 `APP_PORT` 到空闲端口 |
| 5 | 再撞：`bind host port 127.0.0.1:5000` | **另一个项目的后端就跑在 5000** | 换到 18080 |
| 6 | gunicorn 报 `Worker failed to boot`，容器起来又挂 | `wsgi.py` 少了 `sys.path.insert(项目根)`。**本地是 virtualenv 帮忙加的**，容器里没有 virtualenv，gunicorn 又只加「当前目录」 | `wsgi.py` 自己加（配了 `test_wsgi.py` 守着，把 venv 那层保护手动拆掉才测得出来） |
| 7 | 域名访问弹备案拦截页，换端口也一样 | 阿里云按**请求里的域名**查备案，**不分端口** | 用 IP 访问（不触发检查）；要域名只能备案 |

几条经验：

- **`docker compose up -d --build` 失败时，默认的进度条只留一行 `exit code: 1`**。
  加 `--progress plain` 才有逐行输出——不然连它死在哪一步都看不出来
- **长命令用 `nohup ... &` 扔到后台**，`tail -f 日志文件` 看进度。
  挂在 ssh 会话里跑十几分钟的构建，窗口一关就前功尽弃（已经建好的层有缓存，不用从头来）
- **多行粘贴是不可靠的**：`cat > x <<'EOF' ... EOF` 少了最后一行，终端会一直卡在
  `>` 提示符。命令尽量写成单行、不含中文（中文在粘贴里最容易丢），
  配置文件放仓库里用 `cp` 而不是手敲
- **`grep -r` 不跟随软链接**：`/etc/nginx/sites-enabled/` 里全是软链接，
  查配置要用 `cat /etc/nginx/sites-available/xxx`
