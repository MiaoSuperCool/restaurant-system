# 部署（Docker）

一台云服务器 + Docker，把后端和三个前端装进一个镜像跑起来。
这份文档是**照着实操顺序**写的，每一步都标了「在哪儿执行」和「看到什么算对」；
最后那张**排查表**是这次真机部署踩出来的，比前面的步骤更值得看。

---

## 一、部署完是什么样

```
                      ┌─────────────────────────────────────┐
   浏览器 ──→ nginx ──→│  容器 app                           │
              :80      │    gunicorn ──→ Flask               │
                       │      ├── /          内部人员网页端   │
                       │      ├── /customer/ 顾客端（H5）     │
                       │      ├── /staff/    员工端（H5）     │
                       │      └── /api/*     接口             │
                       └──────────┬──────────────────────────┘
                                  │
                       ┌──────────┴──────────┐
                       │ 容器 db (MySQL 8)    │  ← 数据在 volume 里
                       │ 容器 redis           │
                       └─────────────────────┘
```

三个前端**塞在同一个域名下**，各占一段路径——这样不用配跨域，别人也只要记一个地址。
路径前缀是**构建时**写死的（两个 uni-app 的 `H5_BASE`，见各自 `vite.config.ts`）。

两个小程序端放的是 **H5 版**：真机要正式 AppID + 备案域名，求职作品没有这些，
而 H5 是同一套代码编出来的，界面和交互一样。

## 二、先判断：你的机器走哪条路

```bash
free -h        # 看 Mem 那行的 total
```

| 内存 | 走哪条路 | 为什么 |
| --- | --- | --- |
| **≥ 4G** | 常规：`docker compose up -d --build` 一条命令从源码构建全部 | 省心 |
| **1~2G** | **小内存路线**：三个前端在你自己电脑上构建好、打包传上去，服务器只装 Python | 见下面【第 10 条】 |

**1~2G 的机器上，常规路线会把机器打满到 ssh 都登不进去**——不是"慢一点"，
是得去云控制台强制重启。原因有两个，都是真机踩出来的：

1. BuildKit 会把**没有依赖关系的构建阶段并行跑**（三个前端 = 三份 `npm ci` 同时开跑）
2. 一个 node 构建峰值七八百兆，1.6G 的机器根本装不下

（仓库里的 Dockerfile 已经把三个阶段合并成一个来串行执行，但内存太小的机器还是别赌。）

## 三、按顺序做

> 下面每一步都标了在**哪个窗口**执行。命令**一条一条粘**，
> 别把几条攒在一起——尤其**不要用 `cat > 文件 <<EOF ... EOF` 这种多行写法**，
> 从聊天窗口/文档里复制时少一行（尤其结尾那个 `EOF`）终端会一直卡在 `>` 提示符，下不来。

### 【第 1 条】装 Docker（服务器）

```bash
curl -fsSL https://get.docker.com | sh
```

**大陆服务器这一条大概率失败**：脚本要去 `download.docker.com` 下 GPG 公钥，
那个域名经常被 reset（报 `OpenSSL SSL_connect: Connection reset by peer`）。
换成阿里云的镜像源装：

```bash
apt-get update && apt-get install -y ca-certificates curl gnupg
```

```bash
install -m 0755 -d /etc/apt/keyrings
```

```bash
curl -fsSL https://mirrors.aliyun.com/docker-ce/linux/ubuntu/gpg -o /tmp/docker-key.asc
```

```bash
ls -l /tmp/docker-key.asc && head -1 /tmp/docker-key.asc
```

→ 大小 2000 多字节、第一行是 `-----BEGIN PGP PUBLIC KEY BLOCK-----` 才算下对了

```bash
gpg --dearmor -o /etc/apt/keyrings/docker.gpg /tmp/docker-key.asc && chmod a+r /etc/apt/keyrings/docker.gpg
```

```bash
echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/docker.gpg] https://mirrors.aliyun.com/docker-ce/linux/ubuntu jammy stable" > /etc/apt/sources.list.d/docker.list
```

> `jammy` 是 Ubuntu 22.04 的代号，别的版本用 `lsb_release -cs` 查一下替换。
> **文件名必须是 `.list` 结尾**：粘断了变成 `docker.li` 之类的，
> apt 会忽略它（只给一句 `N: Ignoring file ... invalid filename extension`），
> 后面报「找不到 docker-ce」你就会一头雾水。

```bash
cat /etc/apt/sources.list.d/docker.list
```

→ 确认以 `stable` 结尾、文件名是 `.list`

```bash
apt-get update
```

→ **不该出现 `NO_PUBKEY`**。出现了说明公钥没装好，回上面重下

```bash
apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

```bash
docker --version && docker compose version
```

→ 两个版本号都出来才算成（`docker-compose-plugin` 提供 `docker compose`，
少了它后面所有命令都跑不了）

### 【第 2 条】配镜像加速（服务器）

大陆服务器不配这个，拉 `mysql:8.0`、`node:20-alpine` 会慢到像卡死。

去**阿里云控制台 → 容器镜像服务 → 镜像工具 → 镜像加速器**，复制那个 `https://xxxx.mirror.aliyuncs.com`，然后（**一整行，把引号里的中文换成你的地址**）：

```bash
echo '{"registry-mirrors":["你的加速地址"]}' > /etc/docker/daemon.json
```

```bash
systemctl restart docker && docker info | grep -A 3 "Registry Mirrors"
```

→ 能列出你刚填的地址就成了

### 【第 3 条】拉基础镜像（服务器）

```bash
docker pull mysql:8.0
```

```bash
docker pull redis:7-alpine
```

```bash
docker pull node:20-alpine
```

```bash
docker pull python:3.12-slim
```

→ 四条都要 `Pull complete`

**加速器也不是万能的**：它只服务自己缓存过的镜像。碰到 `not found`（`node` 和
`python` 就容易这样），换条通道——用全名从别的镜像站拉，再改成本地短名：

```bash
docker pull docker.m.daocloud.io/library/node:20-alpine
```

```bash
docker tag docker.m.daocloud.io/library/node:20-alpine node:20-alpine
```

（`python` 同理换名字。）Dockerfile 里写的是短名，本地有这个 tag 它就直接用本地的。

### 【第 4 条】拉代码（服务器）

```bash
mkdir -p /opt && cd /opt && git clone <仓库地址> restaurant-system && cd restaurant-system
```

（服务器拉不动 GitHub 的话，在本地 `git archive` 打包再 `scp` 上去。）

### 【第 5 条】写 `.env`（服务器）

**在仓库根目录**，不是 `backend/.env`（那份是本地开发用的）。

```bash
cd /opt/restaurant-system && printf 'DB_PASSWORD=%s\nSECRET_KEY=%s\nAPP_PORT=%s\n' "$(openssl rand -hex 12)" "$(openssl rand -hex 32)" "127.0.0.1:18080" > .env
```

```bash
cat .env
```

→ 三行，`=` 后面都有值

> **为什么用 `printf` 而不是 `cat > .env <<EOF`**：多行粘贴会被截断，
> 少一行就卡在 `>` 上出不来。单行命令没这个毛病。
>
> **`APP_PORT` 为什么是 `127.0.0.1:18080`**：让容器只监听本机，
> 由 nginx 对外。用 18080 不用 5000，是因为 VPS 上常有别的项目占着 5000（踩过）。

### 【第 6 条】小内存机器：传前端产物（本地 → 服务器）

**内存 ≥ 4G 的机器跳过这条。**

**在你自己电脑上**（项目目录里）：

```bash
mkdir -p prebuilt && cp -r web-staff/dist prebuilt/web-staff && cp -r mp-customer/dist/build/h5 prebuilt/mp-customer && cp -r mp-staff/dist/build/h5 prebuilt/mp-staff && tar czf prebuilt-dists.tar.gz prebuilt
```

> 本机还没构建过的话，先跑（**Git Bash 要加 `MSYS_NO_PATHCONV=1`**，
> 不加的话 `/customer/` 会被当成路径转换成 `/Application/Git/customer/`，
> 产物里的资源引用全错）：
> ```bash
> cd web-staff && npm run build
> cd ../mp-customer && MSYS_NO_PATHCONV=1 H5_BASE=/customer/ npm run build:h5
> cd ../mp-staff && MSYS_NO_PATHCONV=1 H5_BASE=/staff/ npm run build:h5
> cd ..
> ```

传上去：

```bash
scp prebuilt-dists.tar.gz root@<服务器IP>:/opt/restaurant-system/
```

服务器上解开：

```bash
cd /opt/restaurant-system && tar xzf prebuilt-dists.tar.gz && ls prebuilt
```

→ 列出 `mp-customer` / `mp-staff` / `web-staff` 三个目录

### 【第 7 条】起（服务器）

**内存 ≥ 4G：**

```bash
cd /opt/restaurant-system && docker compose up -d --build
```

**1~2G 的机器**（用 prebuilt 那套，不跑 node 构建）：

```bash
cd /opt/restaurant-system && docker compose -f docker-compose.yml -f docker-compose.prebuilt.yml up -d --build
```

嫌这条太长，就在 `.env` 里加一行，之后普通命令也能用：

```bash
echo 'COMPOSE_FILE=docker-compose.yml:docker-compose.prebuilt.yml' >> /opt/restaurant-system/.env
```

```bash
cd /opt/restaurant-system && docker compose config | grep -i dockerfile
```

→ **必须看到 `dockerfile: Dockerfile.prebuilt`** 才算生效（没看到就别用这招）

### 【第 8 条】看启动（服务器）

```bash
cd /opt/restaurant-system && docker compose ps
```

→ 三个容器都 `Up`，`db` 和 `redis` 是 `healthy`

```bash
cd /opt/restaurant-system && docker compose logs --tail 30 app
```

→ 四条关键输出：

```
✅ 管理员创建成功: admin
✅ 权限同步完成：新增权限 39 个，新建角色 8 个
✅ 演示数据就绪：门店 6、菜品 15、账号 11、订单 12、班次 18、排班 90
[INFO] Booting worker with pid: ...
```

### 【第 9 条】放行端口（云控制台）

安全组 → 入方向 → 加规则：协议**自定义 TCP**、端口范围 **80/80**（或你 nginx 要用的）、
来源 `0.0.0.0/0`。

**不做这步，前面全对也打不开**——而且现象很像"部署失败"，很多人卡这儿。

### 【第 10 条】nginx 指过来（服务器）

配置文件在仓库里（`deploy/nginx.conf`），**别手敲**：

先把 `YOUR_IP_OR_DOMAIN` 换成服务器的公网 IP（或备案后的域名）——
**命令里刻意不写中文**：中文在粘贴时最容易丢字，一丢 sed 就静默不生效（踩过）。

```bash
cd /opt/restaurant-system && sed -i '16s/.*/    server_name YOUR_IP_OR_DOMAIN;/' deploy/nginx.conf
```

```bash
sed -n '16p' /opt/restaurant-system/deploy/nginx.conf
```

→ 确认第 16 行是你填的 IP / 域名

```bash
cp /opt/restaurant-system/deploy/nginx.conf /etc/nginx/sites-available/restaurant && ln -sf /etc/nginx/sites-available/restaurant /etc/nginx/sites-enabled/restaurant
```

```bash
nginx -t && systemctl reload nginx
```

→ `syntax is ok` + `test is successful`

## 四、出问题查这张表

**全部是真机踩出来的**，按"现象"能直接查。

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| `curl get.docker.com` 报 `Connection reset by peer` | `download.docker.com` 被墙 | 换阿里云源装，见【第 1 条】 |
| apt 说 `Package docker-ce is not available`，还有一句 `N: Ignoring file 'docker.li'` | 软件源文件名被粘断了，apt 不认 | 文件名必须 `.list` 结尾 |
| `apt-get update` 报 `NO_PUBKEY` | GPG 公钥没装好 | 重下公钥，见【第 1 条】（**别用 `curl \| gpg` 管道**，前一半失败看不出来） |
| `npm ci` 失败 `exit code: 1` | 大陆直连 npmjs.org 超时（`npm ci` 不会重试） | `.env` 里加 `NPM_REGISTRY=https://registry.npmmirror.com` |
| 构建到一半卡死、ssh 都登不进去 | 1~2G 内存被并行构建打满 | 加 4G swap + 走【第 6 条】那条本地产物的路 |
| `failed to bind host port 127.0.0.1:3306` | VPS 上本来就跑着 MySQL | 删掉 compose 里 db 的 `ports:`（**已经删了**，本地调试用 `docker compose exec db`） |
| `failed to bind host port 0.0.0.0:80` | 80 被 nginx 占着（可能还有别的项目） | 换 `APP_PORT` |
| `failed to bind host port 127.0.0.1:5000` | 5000 被占（VPS 上很常见） | 换 `APP_PORT=127.0.0.1:18080` |
| 容器起不来，logs 里 `click.exceptions.Abort` / `Aborted!` | `create-admin` 的 `--name`/`--mobile` 带 prompt，容器里没 stdin | 启动命令里把这两个参数补上（**已经补了**） |
| gunicorn 报 `Worker failed to boot`，容器起来又挂 | `wsgi.py` 少了 `sys.path.insert(项目根)`。本地是 **virtualenv 帮你加的**，容器里没有 virtualenv | `wsgi.py` 自己加（**已经加了**，`test_wsgi.py` 守着） |
| 整个机器不响应，**控制台都进不去** | 内存被榨干：MySQL 450M + 4 个 worker 400M | 强制重启 → worker 降到 2 + MySQL 关 performance_schema（**已经改了**）。体检看 `free -h` 的 `available`，别低于 200Mi |
| 改完前端重新部署，浏览器看着还是旧的 | `index.html` 被浏览器缓存 | 后端已经给三个入口加了 `Cache-Control: no-cache` |
| 域名访问弹出「域名暂时无法访问 / 请等待域名备案」 | 阿里云按**请求里的域名**查备案，**不分端口**（换端口也不行） | 用 IP 访问（不触发检查）；要域名只能备案 |
| 命令卡在 `>` 提示符下不来 | 多行粘贴少了结束标记 `EOF` | `Ctrl+C`；以后用单行命令 |
| `grep -r ... /etc/nginx/sites-enabled/` 没输出 | `grep -r` 不跟随软链接 | 去看 `sites-available/` 里的真文件 |
| `scp` 输完密码就卡住 | 服务器本身已经半死不活（多半是内存） | 先救服务器，再传 |

## 五、常用命令

```bash
docker compose ps                          # 三个容器在不在
docker compose logs -f app                 # 看后端日志（Ctrl+C 只退日志）
docker compose restart app                 # 重启应用
docker compose down                        # 停（数据在卷里，不丢）
docker compose up -d --build               # 改了代码之后重新部署

docker stats --no-stream                   # 每个容器吃多少内存（小机器常看）

# 想重新灌一遍演示数据（会清掉订单/会员/排班，再从头建）
docker compose exec app python manage.py seed-demo --reset

# 老系统共存那一摊（对账页要有数据才好看）
docker compose exec app python manage.py import-legacy
docker compose exec app python manage.py reconcile

# 连进数据库看数据（没对宿主机开放端口，这是唯一入口）
docker compose exec db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" restaurant_system'

# 备份
docker compose exec db sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" restaurant_system' > backup.sql
```

**长命令（构建之类）用 `nohup` 扔后台**，别挂在 ssh 会话里：

```bash
cd /opt/restaurant-system && nohup docker compose build --progress plain > /tmp/build.log 2>&1 &
```

`tail -f /tmp/build.log` 看进度，窗口关了也不影响。

> **构建失败时一定要加 `--progress plain`**：默认那个原地刷新的进度条
> 失败时只留一行 `exit code: 1`，死在哪一步都看不出来。

## 六、上线前必须改的两件事

**1. `SECRET_KEY`**（【第 5 条】里已经用 `openssl rand -hex 32` 生成了）。
不换的话 session cookie 可以被伪造。

**2. `admin` 的密码**。默认 `Admin123!`，而这个项目是公开演示、演示账号密码都写在 README 里。
admin 是超管、能删数据，别人拿它登进去能把演示数据清空。
改法：**第一次启动之前**就在 `.env` 里写 `ADMIN_PASSWORD=...`。
已经建过了的话 `create-admin` 只会提示「已存在」不改密码——那时候要登进去在「员工」页
把那个账号删掉，再跑一遍启动脚本。

## 七、域名：备案绕不过去（实测记录）

**结论：大陆服务器 + 没备案的域名，用域名访问就是不通；用 IP 访问完全没问题。**

四条都是实测（2026-09-18）：

```
cestamiao.top              → 能用（服务器上另一个项目，说明这个域名在白名单里）
restaurant.cestamiao.top   → 阿里云备案拦截页
cestamiao.top:18080        → 也拦。非标准端口不放过
http://120.26.65.242/      → 能用 ✓ ← 最终就是这么上线的
```

两个认识，跟网上流传的不一样：

1. **拦截是按「请求里的域名」查的，不分端口。** "换个端口绕过备案"在阿里云这里不成立
2. **用 IP 访问压根不触发这个检查**：备案跟域名绑，Host 里没有域名就没有这回事

备案下来之后（自己的域名 + 自己的服务器，一般 1~3 周），
把 `APP_PORT` 改回 `127.0.0.1:18080`、`server_name` 换成域名，再：

```bash
apt install -y certbot python3-certbot-nginx
```

```bash
certbot --nginx -d 你的域名
```

```bash
echo 'SESSION_COOKIE_SECURE=true' >> /opt/restaurant-system/.env && cd /opt/restaurant-system && docker compose up -d
```

**最后这条的顺序不能反**：上了 HTTPS 再打开它。反了的话 http 下浏览器不回传
cookie，表现是「登录点了没反应」（POST 明明 200，下一个请求却是未登录）。

## 八、这次部署验到了哪一步

| 验过的 | 怎么验的 |
| --- | --- |
| 三个前端能构建出带路径前缀的产物 | 本地 `H5_BASE=... npm run build:h5`，检查产物里的资源引用 |
| 后端能同时托管三个端 | 生产模式下三个路径各返回各的 index.html，深链和静态资源都 200 |
| 三个端在生产模式下真的能用 | 浏览器实测：网页端登录 + 深链；顾客端「首页 → 点餐 → 下单 → 我的」全走一遍 |
| 顾客端能用券 | 未登录 → 登录 → 券出现 → 选中（¥36 → ¥26）→ 提交 → 订单详情应付 ¥26 |
| 真机部署 | 阿里云 2 核 1.6G，走【第 6 条】那条路（本地产物 + prebuilt），最后 IP 能访问 |

**没验的**：Dockerfile 那条完整构建路线（本机没 Docker，小机器也没敢跑）。
它在 CI 里只验了「能构建」，没有真跑起来过——要用它的话，第一次盯着日志看。
