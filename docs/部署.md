# 部署

给「把链接发给别人点开看」这个场景写的。**一台有公网 IP 的云服务器 + Docker**，
三条命令起起来，不需要域名、不需要 HTTPS（要加也写了，见最后一节）。

## 部署完是什么样

一个地址，三个入口，都在这一个域名（或 IP）下面：

```
http://<你的服务器地址>/            内部人员网页端（店长/老板/收银员用）
http://<你的服务器地址>/customer/   顾客端（手机打开：扫码点单那一套）
http://<你的服务器地址>/staff/      员工端（手机打开：代客点单、出单、我的班表）

http://<你的服务器地址>/api/docs    接口文档（Swagger）
```

**为什么是三个路径而不是三个域名**：这三个前端是同一套后端的三个客户端，
放一起就不用配跨域（`FRONTEND_ORIGINS` 留空即可），别人也只需要记一个地址。
路径前缀是**构建时**写进产物里的（两个 uni-app 的 `H5_BASE`，见各自 `vite.config.ts`），
后端只负责照着路径把文件发出去。

**两个小程序端放的是 H5 版**：微信小程序真机要正式 AppID + 备案域名，
求职作品没有这些（`manifest.json` 里的 appid 是空的），
所以线上给别人看的是同一套代码的 H5 产物——界面和交互是一样的。

## 服务器要什么

- 一台能装 Docker 的 Linux（2 核 2G 就够，镜像构建那几分钟吃点内存）
- 装好 Docker Engine + Compose 插件：`curl -fsSL https://get.docker.com | sh`
- 安全组/防火墙放行你要用的端口（默认 5000；用 `APP_PORT=80` 就放行 80）

## 三步

```bash
# 1. 拉代码
git clone <你的仓库地址> restaurant-system && cd restaurant-system

# 2. 写 .env（**在仓库根目录**，不是 backend/.env——那份是本地开发用的）
cat > .env <<'EOF'
DB_PASSWORD=换个数据库密码
SECRET_KEY=换成一串随机的
EOF
# SECRET_KEY 生成方法：openssl rand -hex 32
# **一定要换**：不换就是代码里那个 "change-me"，session 会被人伪造

# 3. 起（第一次要构建三个前端 + 装 Python 依赖，几分钟）
docker compose up -d --build
```

然后浏览器打开 `http://<服务器地址>:5000`，用 `dianzhang / Demo123!` 登录。

看启动过程：`docker compose logs -f app`。

## 容器第一次启动时自动做的事

`docker-compose.yml` 里那串 `command` 就是开机自检流程，顺序是有讲究的：

```
flask db upgrade              建表/迁移
python manage.py create-admin 建超级管理员（admin / Admin123!）
python manage.py seed-rbac    灌权限码和预置角色
python manage.py seed-demo    灌演示数据（--if-empty：库里已有门店就跳过）
gunicorn -w 4                 起服务
```

三个注意点：

- **`seed-rbac` 不能省**。不跑的话所有角色一个权限都没有，登录进去什么都点不动
  （除了 admin，它是超管，绕过权限判断）
- **`seed-demo` 带 `--if-empty`**：订单数据不是幂等的，不带这个每次重启都多 12 笔演示订单
- **`create-admin` 必须把 `--name` / `--mobile` 也传上**。这两个参数带 `prompt`，
  容器里没有 stdin，不传的话 Click 会直接 `Aborted!` 退出，后面那串 `&&` 全都不执行，
  gunicorn 根本起不来（**这个坑真踩过**，在本机复现的）

## 常用命令

```bash
docker compose ps                        # 三个容器在不在
docker compose logs -f app               # 看后端日志
docker compose restart app               # 改了 .env 之后重启
docker compose down                      # 停（数据在卷里，不会丢）
docker compose up -d --build             # 更新代码后重新部署

# 想重新灌一遍演示数据（会清掉订单/会员/排班，再从头建）
docker compose exec app python manage.py seed-demo --reset

# 老系统共存那一摊（对账页要有数据才好看）
docker compose exec app python manage.py import-legacy
docker compose exec app python manage.py reconcile

# 数据库备份（演示数据也是数据，讲砸了还能退回来）
# 密码用容器里那个变量：compose 把它从 .env 的 DB_PASSWORD 传进去了
docker compose exec db sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" restaurant_system' > backup.sql
```

## 上线前请务必改掉的两件事

**1. `SECRET_KEY` 必须换**（上面写了）。不换的话 session cookie 是可以伪造的，
任何人都能把自己改成 admin。

**2. 想清楚 admin 密码**。默认是 `Admin123!`，而这个项目是**公开演示**——
演示账号的密码都写在 README 里（`Demo123!`），有人拿 admin 登进去能把数据删光。
三个选择：

- 演示环境的数据库本来就是一次性的 → **接受它**，但别往里放任何真实数据
- 改掉：**第一次启动之前**就在 `.env` 里写 `ADMIN_PASSWORD=...`。
  已经建过之后 `create-admin` 只会提示「已存在」，它不改密码——
  那时候要改得先进后台（员工页）把这个账号删掉，再跑一遍启动脚本
- 最省事：**别把 admin 的密码告诉任何人**，演示一律用 `laoban` / `dianzhang` 这些演示账号

（`admin` 是超管，能用所有功能；演示账号各有各的角色，**演示权限体系反而更好用它们**——
换个账号登录，菜单和按钮都不一样，这是这个项目最值得看的地方。）

## 加域名和 HTTPS（可选）

上面那套跑在 http 上完全够看。要挂域名/证书的话，让 nginx 顶在前面：

```nginx
server {
    listen 80;
    server_name demo.example.com;

    # 前端产物里写的是 /customer/、/staff/ 这些路径，不用改写，
    # 整套（含 /api）原样转给容器就行
    location / {
        proxy_pass http://127.0.0.1:5000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

证书用 certbot 一行就够：`certbot --nginx -d demo.example.com`。

**上了 HTTPS 之后记得把 cookie 的 Secure 打开**：在仓库根的 `.env` 里写
`SESSION_COOKIE_SECURE=true`（compose 会把它传进容器），然后
`docker compose up -d`。这一步不做也能跑，只是 cookie 在 https 下没带 Secure 标记，
属于「能跑但不该这样」。

> 这一段用到的 `X-Forwarded-Proto` 只在将来要生成外部链接时才有用（现在没有这种功能）。
> 记在这儿是因为**代理层是最容易漏配的地方**，等出问题再回头找就晚了。

## 这次部署验到了哪一步

诚实记一下（**没有 Docker 的机器上做的验证**）：

| 验过的 | 怎么验的 |
| --- | --- |
| 三个前端能构建出带路径前缀的产物 | 本地 `H5_BASE=/customer/ npm run build:h5` 等，检查产物里的资源引用 |
| 后端能同时托管三个端 | 本地按生产配置（`FLASK_ENV=production`）起服务，三个路径各返回各的 index.html，深链和静态资源都 200 |
| 三个端在生产模式下真的能用 | 浏览器实测：网页端登录 + 直接打开 `/schedule`；顾客端「首页 → 点餐 → 订单 → 我的」走一遍；员工端登录页。无控制台报错、无 404 静态资源 |
| `create-admin` 非交互会卡住 | 本机复现（`Aborted!`），已补上 `--name` / `--mobile` |

| **没验的** | 为什么 |
| --- | --- |
| `docker compose up` 本身 | 这台机器没装 Docker。**Dockerfile 的构建逻辑没跑过**——三个前端阶段和最后的 COPY 是新写的，第一步 `docker compose up -d --build` 有可能要调 |
| 服务器上的 gunicorn | Windows 跑不了 gunicorn |

所以第一次在服务器上跑，**盯着 `docker compose logs -f app` 看**。
真出问题多半在前几分钟（构建或启动自检那串命令），那也是最好查的阶段。
